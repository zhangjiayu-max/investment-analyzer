## AI 对话架构：修 pipeline 失败 + 综合改流式（2026-10-21 晚）

### 根因（数据实证，非推断）
- **pipeline 100% 失败的根因是输出上限被预算压成碎片**：`token_usage` 里 `completion_tokens=1333` 精确出现 18 次，横跨 4 个专家、只在 `#turn2`/`#continue`；同期 ReAct 成功请求是 3899/3330/4425 无重复值。
- 机制：`multi_agent._SpecialistUsage.call` 用 `cap = min(cap, remaining - prompt_estimate)`，而 `_estimate_specialist_tokens` 按「字符/2」估算，JSON+英文密集上下文高估约 2.4 倍 → 第三轮输入 2 万 token 时输出被压到 1333，A2A JSON 闭合不了、正文没空间 → output_quality 判 failed。
- 次要因素：A2A JSON 契约过长（asset_actions 7 字段 + data_references），2622 字全是未闭合 JSON，没正文。

### 修复（4 处）
1. `agent/core/multi_agent.py`：用真实 `usage.prompt_tokens` 校准估算比（滑动平均、只收敛不放大）+ 输出下限 `floor=min(cap//2, remaining//2)`。复现三轮 `max_tokens` 恢复 `[8000,8000,8000]`，`estimate_ratio=0.419`。
2. `agent/infra/message_protocol.py`：压缩 A2A 契约措辞（字段名不动，契约测试依赖），要求 JSON≤30 行、action 各≤5 条、正文≥400 字。
3. `agent/infra/output_quality.py`：issue 分「可容忍/致命」两类；`incomplete_completion`/`closure_failed`/`unfinished_ending` 降级即可，`tool_fallback`/空正文/raw tool_call 仍 failed（安全边界不放宽）。
4. 综合阶段改流式：`_synthesize_multiple_specialists` 走 `_call_llm_stream`+`chunk_emitter` 回调 → `_phase_synthesis` 透传 → `_phase_synthesis_streaming`（线程+队列桥接）→ `run_pipeline` yield → `orchestrator` 显式转发 → SSE。

### 关键设计决策
- **不做生成器化**：`_phase_synthesis`/`_synthesize_multiple_specialists` 被 15+ 处测试同步调用并断言返回 tuple/dict，改签名破坏面太大。改用回调注入 + 线程桥接，对外契约零变化。
- **orchestrator 事件映射是白名单 elif 链**，之前 `answer_chunk` 只靠 `else: yield evt` 兜底透传，已改为显式分支。
- `pipeline.synthesis_stream_enabled`（默认 true）；`tests/conftest.py` autouse 关闭，否则只 mock `_call_llm` 的用例会打真实流式通道，单测从 2 秒变 41 秒。
- `answer` 事件会覆盖 `final_content`，所以流式后仍可做 veto/guard 改写，前端以 answer 为准。

### 验证
- 全量：**1842 passed**（+6 新增流式用例）/ 16 failed / 21 errors；失败集合与改动前**逐条一致**（沙箱 PermissionError + 既有 bug）。
- 新增 `backend/tests/test_pipeline_streaming_synthesis.py` 7 用例，含端到端：run_pipeline 真产出 answer_chunk 且拼接=完整答案。

### 环境坑
- macOS 无 `timeout` 命令（用 Bash 工具自带超时）。
- pytest 在沙箱下默认 `--basetemp` 会 PermissionError，需显式 `--basetemp=/tmp/xxx`；`tmp_path` 相关 ERROR 是环境既有，非代码问题。
- 判断测试是否是自己弄坏的：`git stash` 前后各跑一次 `pytest --lf` 比对失败集合。

## RAG 对对话分析的实际增益诊断（数据实测）

用只读方式查 data/valuations.db（161MB，主库），结论：RAG 管线可用且被高频使用，但增益被三个结构性断层吃掉。

### 链路现状
conversations.py:1424 预检索（原始 effective_query，单次 hybrid）→ orchestrate_stream(prepared_rag_context) → pipeline._phase_info_gather 的 _rag_task 因 `prepared_rag_context is not None` **整段短路**（跳过 `_enhance_rag_query` + 子查询展开 + intent 驱动 content_types + 去重排序 + low_quality 提示）→ 专家 system prompt（`## 知识库参考`，max_tokens_rag_compress=1500）+ agentic search_knowledge（MAX_TURNS=3，检索轮次上限 2）。

### 实测数据
- knowledge_fts 池：book 8214 / analysis 911 / note 579 / article 398 / author_article 125 / valuation 100
- search_knowledge 调用 918 次，success 99%，空结果仅 1%，耗时中位 224ms → 工具本身很可用
- 专家**主动**限定 `content_types=['book']` 达 412 次（45%）——源自 `_ACTIVE_RETRIEVAL_INSTRUCTION` 强制场景写死 `["book","analysis"]`
- rerank 生效：首条分中位 0.878；但 book 占检索结果 47%，49% 的对话 book 占 60%+
- 预检索 content_types 为空（全类型）占 46%
- knowledge_base 的 book：as_of_date / limitations / counterpoints **8214 条全空** → RAG context 无法标注"书籍理论非当期事实"
- analysis_records 1604 条 success，仅 911 条进 FTS，**566 条有实质内容的未索引**（含中证白酒/恒生/红利低波，时间到 2026-10-21）；`index_analysis_to_rag` 只被 `reindex_all_analysis_records` 手动批量调用，**无入库自动索引钩子**
- pipelines low_quality 判定 `any(r.quality_status != usable)` 过严 → 13 条标记里 10 条（77%）首条分>=0.5 是误伤
- 已有评测 data/rag_eval_results.json：15 例，precision 0.71 / recall 0.93 / MRR 0.50 / ndcg 0.79（MRR 偏低=排序问题）
- rag_logs 584 条，rag_feedback 0 条（反馈闭环未启用）

### 优先级建议
1. 消除预检索短路（让 intent 映射 + 子查询展开生效）— 直接解决 46% 全类型
2. low_quality 判定改为基于 top1 分数 — 避免误伤抑制模型使用 RAG
3. 补 566 条分析记录索引 + 加入库自动索引钩子（最高性价比供给增量）
4. book 补齐 as_of_date/limitations 并在 context 标注"理论非当期数据"
5. 改 `_ACTIVE_RETRIEVAL_INSTRUCTION`：估值判断场景不该查 book，应查 analysis+valuation
