# 会话 205、206、207 评测与降级原因审计

评测日期：2026-10-21。范围：本地数据库中的原始消息、专家执行记录、SSE 事件、模型用量、交易记录，以及当前代码。未重新生成投资回答，未调用新的投资分析模型，未触发提示词进化或修改交易数据。

## 结论

“有结果”与“执行失败”同时出现，是因为系统保留了降级正文，但把所有非 completed 的结果都映射为 failed。206、207 的综合正文已生成并正常收尾，未通过的是整体质量验收：专家全部截断、审查预算耗尽。这不能只通过去掉报错来解决。

另外确认了一个更高优先级的数据问题：假设交易被注入为真实成交，影响了“近期频繁加仓”“冷却期”等投资判断。当前三条回答均不应作为经过完整核验的交易方案。

## 报错链路与根因

1. 两次 SSE plan 事件均显示 medium。medium 的 execution 预算为 4,000，三位并行专家分摊后每次输出上限为 1,333 token。实际 token_usage 显示：206、207 每位专家的正文阶段和两次续写均达到 1,333 上限。输出预算还要容纳模型思考，正文长度因此可能很短；207 的资产配置师最终仅留下 112 字。
2. 专家通过 `_SpecialistUsage` 统计输入加输出，但 `_specialist_output_limit` 又把 execution 额度作为每次输出上限使用。每轮实际输入通常已达约 9,000～29,000 token，明显超出原先的阶段预算尺度。
3. 专家阶段累计 usage 使 `_review_tokens_remaining` 返回零；反思直接返回 budget_exhausted，交叉审查亦未完成。审查问题最终写成 `quality_issues=["cross_review_budget_exhausted"]`。
4. 综合器仍能生成正文，但 `_validate_synthesis` 会因失败专家/失败审查降级，`_validate_final_facts` 也会因交叉审查未完成降级。
5. 路由 `_save_final` 将所有非 completed 状态写为 execution_status=failed，并统一使用“综合报告未完整完成……”文案。前端于是显示“执行失败”，造成“正文存在但执行失败”的困惑。
6. 复杂度更新也存在不同步风险：规划后会更新 effective_complexity，但没有同步重新分配 state.token_budget。当前样本 plan 为 medium、最终 metadata 为 complex；应统一复杂度、预算和展示口径。

## 优化项（按优先级）

### P0：假设交易污染真实成交上下文

207 报告称 2026-10-20 已确认买入机器人约 4,386 元、恒生科技约 8,381 元、畜牧养殖约 4,970 元、消费红利约 4,249 元，总计约 21,986 元，并据此认定触发冷却期。对应原始记录：

| transaction id | 基金 | 金额 | status | is_hypothetical |
|---|---|---:|---|---:|
| 680 | 020256 | 4,385.71 | confirmed | 1 |
| 681 | 013309 | 8,381.31 | confirmed | 1 |
| 682 | 012725 | 4,970.28 | confirmed | 1 |
| 683 | 008929 | 4,248.77 | confirmed | 1 |

总额 21,986.07 元，与正文精确对应。这些都是假设交易；confirmed 字段不能覆盖 is_hypothetical 标志。

根因已定位到 `backend/services/portfolio/portfolio_context.py` 的“最近交易记录”SQL：仅过滤 user_id 和 confirmed/pending，未排除 is_hypothetical、is_system，输出时还省略这两个标志。工具侧 `query_transaction_history` 已排除假设交易，导致同一回答得到互相矛盾的两套交易上下文。206 中“流水可能滞后”的解释没有证据，不能用于消解这种冲突。

建议统一调用已有真实交易查询入口；真实成交、待确认、假设方案分别保留来源和状态；冷却期、频率和行为诊断仅用符合条件的真实交易。验收应覆盖上述四条记录，确认它们不会再被描述为“已执行加仓”。

### P1：统一预算口径，保障专家收尾和必要审查

不要直接取消质量门禁，也不要只提高一个 max_tokens。应区分输入成本预算与正文/思考输出预算，按工具往返轮次计费；规划复杂度变更后同步预算；为专家最终答复、结构化 JSON 和审查保留空间。续写需要随剩余额度调整，避免每次固定 1,333 token 又重复发送整个大上下文。

通过按标的和问题选择证据、跨阶段共享 evidence_id、对持仓/工具返回做结构化摘要，降低综合输入。压缩必须保留指标类型、单位、日期、交易真实性等关键字段。

### P1：区分“已生成但待复核”与真正执行失败

已生成的降级结果应展示为“分析已生成，部分核验未完成”，并明确列出“专家分析被截断”“预算不足，交叉审查未完成”等原因。空答、连接异常、取消、重启中断另行展示。下游操作候选仍由 quality_status 把关，不能因为文案调整放行。

### P1：unknown 不能变成专家共识

两条仲裁均显示三位专家 verdict=unknown、confidence=0，却写成“专家立场一致”和“0 位专家立场一致支持该方向”。`arbitration.py` 在无有效方向时默认进入 consensus 分支。实测使用 207 原始专家对象可复现：final_stance=watch、arbitration_mode=consensus、supporting_agents=[]。

建议保留 watch 作为保守兜底，但仲裁状态必须是“证据不足/无法形成裁决”；无效或截断专家不参与支持票数统计，也不能因存在仲裁卡片给协作质量加分。

### P1：修正投资推理与用户意图

- 205 问的是“为什么跌、是否有做空”，专家虽声明缺乏资金和做空数据，却又推断“资金撤离+情绪踩踏”，并给出每期 2,000 元或每月 1,000 元等交易方案。应先回答归因问题，将机制假设与有证据的事实分开，避免未经请求扩大为交易方案。
- 206/207 的保守方向有合理依据：权益代理占比高于已记录目标、当期行情/部分估值数据不全；但这不等于其全部论证正确，尤其不能继续采用错误的近期交易和行为诊断。
- 207 写“除非先降低权益目标”才能加仓，方向相反。降低目标会使超配更严重，应讨论降低实际权益敞口，或经用户明确决策调整目标；不能为了得出可以买的结论而自动改风险目标。
- 207 把目标权益比例和单标的上限都当成同等硬限制，并突然要求将目标上调至至少 25%。应区分配置目标、允许偏离范围和硬上限，目标变更需要画像评估依据。
- 207 用上一交易日行情质疑用户当天上午的“大跌”，又将机器人上一日 +2.98% 写成“今日”反弹。应明确盘中行情未获取，不能用昨收反驳当日观察。
- 207 正文出现重复的“分歧点 2”接缝，说明有限续写虽保留正文，尚需做边界去重和结构收尾检查。

### P2：评测器本身也需要校准

当前规则评测对三条回答的 response、completeness 均给出 100，主要依赖标题、数字、关键词和长度；206/207 把仲裁卡片也算进专家数，协作得 80；`cross_review_budget_exhausted` 被归入事实问题，并设置 has_data_contradiction=true。这会把“尚未核验”误说成“已有事实矛盾”，也掩盖“排版完整但专家截断”的问题。

建议分别记录交付完成度、审查覆盖、事实核验、任务相关性；仅统计有效专家；工具返回 unknown/data_points=0 不应等同于获得可用数据。保留交付门槛，但不能把 49 分上限当成内容质量的精细测量。

## 验证与边界

已运行现有 ConversationQualityEvaluator，对最新 message 612、614、616 逐条评测，关闭 trigger_evolution；另用原始样本和当前函数完成三个最小复现：4,000/3 的输出上限及审查归零、全 unknown 仲裁伪共识、持仓上下文把假设交易显示为已确认。四笔假设买入金额也与数据库逐条核对。

本轮完成评测和原因定位，未修改业务代码、既有回答、用户风险目标或交易记录。相关规则评测和复现证据见同目录 JSON 文件。后续修复应按“真实交易过滤 → 预算/上下文 → 交付文案与仲裁 → 评测校准”的顺序实施，并分别回归验证。
