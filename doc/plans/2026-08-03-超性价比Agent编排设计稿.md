# 超性价比 Agent 编排设计稿

> 日期：2026-08-03
> 目标：将"超性价比指数筛选"从纯规则评分升级为"规则筛选 + Agent 编排解读"
> 核心原则：**规则评分负责精准筛选（无幻觉），Agent 负责编排多工具 + 深度解读**

## 一、现状与问题

### 1.1 现状

[backend/routers/market/valuation.py:451](file:///Users/xiaoyuer/projects/investment-analyzer/backend/routers/market/valuation.py#L451) 的 `/valuation/super-value` 接口：

- **机制**：纯规则评分（5维度：百分位30 + 连续跌25 + 跌幅20 + Zscore15 + 趋势10）
- **数据源**：`index_valuations` 表（螺丝钉 dd_ + 雷牛牛图片解析）
- **已有增强**：多 metric_type 选择（PE/PB/PS/股息率）、数据时效过滤（>10天跳过）
- **已有 LLM 接口**：`/valuation/enhanced-strategy`（判断真低估/价值陷阱/催化剂）
- **前端问题**：超性价比 tab 只展示规则评分结果，enhanced-strategy 结果未展示

### 1.2 问题

| 问题 | 表现 |
|------|------|
| 数据可能过期 | 库内数据 >10 天直接跳过，但用户想看的指数可能因此被漏掉 |
| 单一数据源 | 只用库内（螺丝钉+雷牛牛），不主动补在线最新 |
| 缺乏深度解读 | 规则评分只给分数，不解释"为什么低估""催化剂是什么""能不能买" |
| LLM 结果未展示 | enhanced-strategy 已有 LLM 解读，但前端没接到超性价比 tab |

### 1.3 认知纠正

- ❌ "LLM 让数据更精准" — LLM 是语言模型，不产生市场数据，算百分位会幻觉
- ❌ "结合雷牛牛+螺丝钉" — super-value 已经在用这两个数据源
- ✅ 真正增量：在线查询补全过期数据 + Agent 编排多工具 + LLM 深度解读

## 二、目标定位

```
旧：规则评分（5维度打分）→ 按分数排序展示
新：规则评分（筛选候选）→ Agent 编排（补数据+预测+解读）→ 结构化输出
```

**不做的事**：
- LLM 不做数值筛选（不让 LLM 从100个指数里"挑性价比高的"）
- LLM 不做数值计算（不让 LLM 算百分位、Z-score）
- 不替代 super-value 规则评分（保留作为客观基础）

**要做的事**：
- Agent 编排：调规则评分工具 → 对 top 候选补在线数据 → 调预测信号 → LLM 综合解读
- 前端整合：规则评分卡片 + Agent 深度解读条 一起展示

## 三、架构设计

### 3.1 数据流

```
用户点"深度解读"按钮
    ↓
[HTTP] POST /api/valuation/super-value-deep
    ↓
[规则评分] 调 scan_super_value 工具 → 得到候选列表（分数排序）
    ↓
[在线补数据] 对 top10 候选调 query_online_valuation
    ├── 库内数据新鲜（≤3天）→ 跳过在线查询
    └── 库内数据过期（>3天）→ 查 akshare 补最新 PE/PB
    ↓
[预测信号] 对 top10 候选调 query_valuation_forecast
    └── 得到均值回归信号 / 极值预警
    ↓
[LLM 综合解读] 输入：规则评分 + 在线数据 + 预测信号
    └── 输出：每个指数的"真低估/价值陷阱 + 催化剂 + 操作建议 + 置信度"
    ↓
[返回] 结构化 JSON（规则评分 + 解读）
```

### 3.2 关键原则

1. **规则评分是基础**：Agent 不修改分数，只用分数排序选候选
2. **在线查询是补全**：只补过期数据，不作为筛选依据（在线数据无历史百分位）
3. **LLM 只解读**：输入客观数据，输出定性判断 + 操作建议
4. **开关控制**：符合项目规范，LLM 相关开关默认 false

### 5.2 System Prompt（存 analysis_agents 表）

```
你是估值机会筛选官，负责对超性价比指数做深度解读。

## 工作流程
1. 调用 scan_super_value 获取规则评分候选列表
2. 对 top10 候选，检查 data_freshness：
   - stale_days > 3 → 调用 query_online_valuation 补最新数据
   - stale_days ≤ 3 → 使用库内数据
3. 对 top10 候选调用 query_valuation_forecast 获取均值回归信号
4. 综合三方数据输出解读

## 输出要求（严格JSON）
对每个指数输出：
{
  "index_name": "指数名",
  "index_code": "代码",
  "rule_score": 85,                    // 规则评分（来自 scan_super_value，不可修改）
  "online_pe": 15.2,                  // 在线最新PE（若查询了）
  "online_data_date": "2026-08-03",   // 在线数据日期
  "forecast_signal": "均值回归",       // 来自 query_valuation_forecast
  "opportunity_type": "真低估|价值陷阱|趋势性下行",
  "catalysts": ["催化剂1", "催化剂2"],
  "action": "立即买入|分批建仓|观望|回避",
  "action_detail": "2-3句操作建议",
  "confidence": "high|medium|low"
}

## 红线
- 不可修改 rule_score（规则评分是客观基础）
- 不可编造估值数据（在线查询失败时标注"数据缺失"并降低 confidence）
- 不可对库内未覆盖的指数做解读（只解读 scan_super_value 返回的候选）
```

### 5.3 不进入 multi_agent 编排

**重要**：此 Agent 不加入 `SPECIALIST_AGENTS` 的默认编排，避免每次对话都触发。它只通过专用 HTTP 接口按需调用。

**原因**：
- 超性价比筛选是按需操作，不是每次对话都需要
- 避免增加对话路径的 LLM 成本
- 符合"LLM 调用必须有开关"规范

## 九、成本与性能

| 维度 | 规则评分（现有） | Agent 深度解读（新增） |
|------|-----------------|----------------------|
| 耗时 | <100ms | 5-15秒（含在线查询+LLM） |
| LLM 调用 | 0 | 1次（综合解读） |
| 在线请求 | 0 | 最多10次（仅过期候选） |
| 触发方式 | 自动 | 手动按钮 |
| 开关 | 无 | 默认 false |

**成本控制**：
- top_n 限制为10（只对前10做深度解读）
- 在线查询仅对过期数据（>3天）触发
- LLM 只调用1次（综合解读），不对每个指数单独调用

## 十一、风险与约束

| 风险 | 应对 |
|------|------|
| LLM 幻觉 | 规则评分不可修改；在线查询失败时标注"数据缺失" |
| 在线查询慢 | 仅 top10 + 仅过期数据；超时15秒降级 |
| Agent 不进入对话编排 | 只通过专用接口调用，不影响对话路径 |
| 数据源不一致 | 库内螺丝钉+雷牛牛为主，在线 akshare 为补全，冲突时以库内为准 |
| 开关默认关闭 | 符合项目规范，用户按需开启 |

## 十二、待确认决策点

1. **在线查询范围**：默认"仅 top10 过期候选补数据"。备选：全量候选补数据（成本高）/ 不查在线（数据可能过期）。设计稿按推荐默认，评审时可调整。
2. **Agent 是否进入对话编排**：设计稿选择"不进入，只按需调用"。备选：进入编排但路由器只在用户明确问"超性价比"时触发。
3. **enhanced-strategy 去留**：设计稿保留（独立接口）。备选：废弃，全部走新接口。
