# AI 对话架构审计报告（数据驱动）

> 审计对象：`backend/` 对话链路
> 数据来源：`data/valuations.db`（只读），覆盖 2026-05-31 ~ 2026-10-21
> 方法：静态读码 + AST 结构验证 + 真实运行数据交叉验证
> 说明：本轮只分析，未修改任何代码

## 一、结论摘要

1. **真实性能远低于预期**：complex 请求 P50 210 秒、P95 577 秒，34.8% 超过 5 分钟。
2. **主路径没有流式输出**：所谓"流式对话"的最终答案是一次性生成的，用户全程对着进度圈等待。
3. **Pipeline 路径上线即失败**：最近切换后 2 次请求 100% 失败，根因是专家输出契约冲突。
4. **上一轮报告中三处判断需要修正**（见第六章）。

## 三、最重要的发现：主路径没有流式

### 3.1 代码证据

两条路径的最终答案生成方式完全不同：

| 路径 | 函数 | 调用 | 是否流式 |
|---|---|---|---|
| ReAct | `_stream_final_synthesis` | `_call_llm_stream`（orchestrator.py:5702） | 是，yield `answer_chunk` |
| Pipeline | `_synthesize_multiple_specialists` | `_call_llm`（pipeline.py:3063） | 否，一次性返回 |

而 `system_config` 中 `pipeline.pipeline_enabled = true`。

### 3.2 影响

- 107 秒的生成过程对用户完全不可见
- 6746 字答案在最后 1 秒内一次性推送到前端
- 答案体量 P50 仅 2299 字（`messages` 表 236 条 assistant 消息）

这解释了架构里几个"反常"设计的存在理由：
- `conversation.warn_at_minutes = 5`（5 分钟提示）——因为用户会以为卡死
- SSE 每 15 秒发 `ping` 注释保活——因为没有真实数据流
- 前端 `StreamIndicator` 组件——替一个不存在的流式做动画

### 3.3 收益预估

若将 synthesis 改为流式：总耗时不变，但首字延迟可从 236 秒降到 2–5 秒。**这是全链路投入产出比最高的单点改动。**

## 四、Pipeline 上线即失败

### 4.1 事实

| 时间 | 路径 | 状态 | 耗时 |
|---|---|---|---|
| 2026-05-31 ~ 2026-10-18 | ReAct（148 次） | 全部 completed | P50 217 s |
| 2026-10-20 23:22 | Pipeline | **failed** | 225.9 s |
| 2026-10-21 12:37 | Pipeline | **failed** | 236.4 s |

Pipeline 共触发 2 次，2 次全失败，`error_category = quality`。

### 4.2 失败构成

```json
{"rag_coverage": 0.0, "rag_usable_count": 7, "rag_low_quality": true,
 "tool_success_rate": 1.0, "specialist_completion": 0.0,
 "specialist_count": 3, "review_count": 0, "tool_count": 28}
```

对比成功样本：

```json
{"rag_coverage": 1.0, "tool_success_rate": 1.0,
 "specialist_completion": 1.0, "specialist_count": 6, "tool_count": 9}
```

三个专家全部 `failed`：

| 专家 | 耗时 | result 长度 | tool_calls 字段 |
|---|---|---|---|
| valuation_expert | 96.0 s | 2622 字（纯 JSON，被截断） | 75.6 KB |
| risk_assessor | 101.6 s | 1562 字 | 60.6 KB |
| allocation_advisor | 102.5 s | **112 字** | 93.6 KB |

### 4.3 根因：输出契约冲突

`agent/infra/output_quality.py:analysis_issues()` 的判定规则：

```python
# 剔除 ```json 块后若有正文则为合法
prose = re.sub(r'```(?:json)?\s*\n.*?\n```', '', text, flags=re.DOTALL).strip()
if isinstance(json.loads(prose), (dict, list)):
    issues.append('structured_data_without_analysis')
if len(prose) < min_chars:      # min_chars=50
    issues.append('empty_or_short_analysis')
```

而 `multi_agent.py:636` 又强制注入：
```python
system_content += get_a2a_output_instruction()   # 要求输出 A2A 结构化 JSON
```

**冲突**：系统一边要求专家输出结构化 JSON，一边要求"JSON 不能替代分析正文、prose 必须 ≥50 字"。当 LLM 只输出 JSON（且被 `max_tokens` 截断）时，判定必然失败。

失败链：

```
专家只输出 ```json 块 → 去掉 JSON 块后 prose 为空
→ structured_data_without_analysis + empty_or_short_analysis + unfinished_structure
→ validate_specialist_output 判 invalid
→ specialist_completion = 0.0
→ review_count = 0（审阅被跳过）
→ 整体 quality_status = degraded → execution_status = failed
```

### 4.4 数据异常的次要说明

- `rag_coverage = 0.0` 但 `rag_usable_count = 7`：`rag_low_quality = true` 一票否决，度量不能反映真实覆盖（`conversations.py:3071`）。
- `tool_count = 28`（成功样本仅 9）：工具调用量是成功的 3 倍，context 膨胀使单个专家从均值 59 秒拖到 96–103 秒（约 1.6 倍）。

# 修复记录（2026-10-21 第二轮）

审计发现 pipeline 路径 100% 失败。按「先修可用性、再改流式」的顺序处理，四处改动全部有数据证据支撑。

## 修复 1：专家输出被预算压缩成碎片（P0）

**现象**：10-20、10-21 两次 pipeline 请求全部 failed，专家 `specialist_completion=0.0`。

**证据**：`token_usage` 中 `completion_tokens=1333` 精确出现 18 次，横跨 4 个专家、只出现在 `#turn2` 与 `#continue`：

| caller | out | in |
|---|---|---|
| `valuation_expert#turn2` | **1,333** | 21,852 |
| `risk_assessor#turn2` | **1,333** | 18,117 |
| `allocation_advisor#continue` | **1,333** | 27,949 |
| `valuation_expert#continue` | **1,333** | 23,107 |

而同期 ReAct 路径（10-18，成功的请求）专家输出是 3,899 / 3,330 / 4,425，无重复值。1333 不是模型自然停止，是被人为压出的上限。

**根因**：`multi_agent._SpecialistUsage.call` 用预算余量反推单次输出上限：

```python
cap = min(cap, remaining - prompt_estimate)
```

`_estimate_specialist_tokens` 按「字符数 / 2」估算，JSON 与英文密集上下文会被高估约 2.4 倍。第三轮输入涨到 2 万 token 后，估算吃掉全部余量，`max_tokens` 被压到 1333 —— A2A JSON 块闭合不了，正文没有空间，`output_quality` 判 failed。

**修复**（`agent/core/multi_agent.py`）：
1. 用真实 `usage.prompt_tokens` 校准估算比例（滑动平均，只收敛不放大），消除系统性高估；
2. 保留「一次完整输出」下限 `floor = min(cap//2, remaining//2)`，不允许压到半截值；
3. 真实超支仍由 `reported + estimated > budget` 事后标记 `exhausted`。

**验证**：复现三轮调用，`max_tokens` 恢复为 `[8000, 8000, 8000]`，校准比 `estimate_ratio=0.419`（实测 21852/52478=0.416）。

## 修复 2：A2A JSON 契约挤占正文（P1）

**证据**：10-21 的 `valuation_expert` 输出 2622 字**全部是未闭合 JSON**，没有 Markdown 正文。契约要求 `asset_actions`（含 7 个子字段）+ `data_references` 逐条列举，JSON 本身就消耗 2000+ token。

**修复**（`agent/infra/message_protocol.py`）：字段名与结构不变（下游解析与契约测试依赖），压缩示例与措辞，并新增硬约束——JSON 控制在 30 行内、`action_signals`/`asset_actions` 各不超过 5 条、**正文不少于 400 字**且明确为主要交付物。

## 修复 3：截断判定过严（P1）

**现象**：正文完整、只是结尾被截断的专家被判 `failed`，整链失败。

**修复**（`agent/infra/output_quality.py`）：把 issue 分成「可容忍」与「致命」两类。`incomplete_completion`、`closure_failed`、`unfinished_ending` 等只降级为 `degraded`；空正文、兜底文案、原始 tool_call、结构未闭合、**工具证据冒充分析**仍判 `failed`（安全边界不放宽）。

**验证**：`tool_fallback` → failed；完整正文但 truncated → degraded；空正文 → failed；raw tool_call → failed。

## 修复 4：综合阶段改流式（P0-体验）

**证据**：`stream_events` 中 `answer_chunk` 覆盖率 0%。10-21 那次 107 秒的生成过程前端一个 chunk 都没收到，只在 `+218s` 收到一次性 6746 字。

**改动链路**（四处，缺一不可）：

| 层 | 文件 | 改动 |
|---|---|---|
| 生成 | `agent/core/pipeline.py` `_synthesize_multiple_specialists` | 优先 `_call_llm_stream`，经 `chunk_emitter` 回调吐出增量；失败自动回退非流式续写 |
| 透传 | 同文件 `_phase_synthesis` | 接收并透传 `chunk_emitter` |
| 桥接 | 同文件 `_phase_synthesis_streaming` | 后台线程执行同步综合，队列把事件转给生成器（保持 `_phase_synthesis` 同步契约不变） |
| 转发 | `agent/core/orchestrator.py` | 事件映射显式增加 `answer_chunk`/`reasoning_chunk` 分支 |

**为什么不直接生成器化**：`_phase_synthesis` / `_synthesize_multiple_specialists` 被 15+ 处测试同步调用并断言返回 tuple/dict。改签名的破坏面太大，因此用回调 + 线程桥接，对外契约零变化。

**开关**：`pipeline.synthesis_stream_enabled`（默认 true）。单元测试在 `conftest.py` 统一关闭，避免只 mock `_call_llm` 的用例误打真实流式通道。

**验证**：新增 `tests/test_pipeline_streaming_synthesis.py` 7 个用例，含端到端 —— `run_pipeline` 迭代时真的产出 `answer_chunk`，拼接结果等于完整答案，且最终 `answer` 事件仍携带全文（前端以它为准，后处理改写可覆盖）。

# 修复记录（框架层，同日第三轮）

用户追问「框架类 / agent 配合是否都修了」后逐项核实：上一轮只修了功能可用性，架构债未动。本轮处理三项，并纠正一处误判。

## 修复 5：断点续接恢复（此前完全失效）

**证据**：`orchestration_checkpoints` 表 **0 行**，从未写入。AST 定位：`_save_checkpoint(..., "experts_done")` 位于 `for turn` 循环（6314–6760）**之外**（6763 行），循环内调用次数为 0。

**为什么必然失效**：正常完成路径在循环内 `if ntc_done: return`（6394 附近）直接退出。该分支先由 `_stream_handle_no_tool_calls` 跑完交叉审阅/仲裁/综合，然后 return —— 永远走不到循环之后的存档语句。只有"轮次耗尽"这种异常路径才会经过它，而那条路本身罕见。

循环内的提前退出点共 6 处（`return` 6309/6330/6352、`break` 6350、`continue` 6431/6454），其中 6352 是最常见的正常收尾。

**修复**（`agent/core/orchestrator.py`）：
1. 抽出闭包 `_checkpoint_experts_done()`，捕获当时的 `blackboard` / `specialist_results` / `llm_messages` 等局部状态（闭包读的是引用，调用时取最新值，无需改签名传参）；
2. 在 6352 的 `return` 之前调用；
3. 循环外的原位置保留为「轮次耗尽」兜底。

**验证**：新增 `tests/test_orchestrator_checkpoint.py` 4 个用例 —— 写入通路可用（真写表并读回）、调用点位于循环内、调用点在早退 return 之前、空 conv/message id 时静默跳过。

## 纠正：全局黑板并发串数据 —— 不成立

上一轮判定「`blackboard.py` 是进程级单例，两人同时提问会互相清空」。复查发现 `get_global_blackboard()` **零调用**：只有定义，没有任何代码读取 `_global_blackboard`。`reset_global_blackboard()` 每次请求把它从 `None` 设为 `None`，纯空操作。

真实架构一直是每请求实例：`orchestrate_stream` 里 `Blackboard(max_entries=6)`、`run_pipeline` 里 `Blackboard(max_broadcasts=...)`，并随 checkpoint 序列化 `blackboard_dict`。**并发安全本来就满足。**

处理（`agent/infra/blackboard.py` + 两处 import + 三处调用）：删除该单例三件套，原位置改为显式注释说明"黑板按请求创建，不要引入进程级单例"。这条注释比删掉的代码更有价值——避免下一个人再把它加回来。

## 修复 6：超时阈值统一（600s → 300s）

**证据**（857 次专家运行实测）：

| 指标 | 值 |
|---|---|
| P50 | 58.8s |
| P95 | 116.8s |
| P99 | 153.2s |
| max | 273.9s |
| ≥300s 的次数 | **0** |

而 `agent.specialist_timeout` 是 **600s** —— 比实测峰值高一倍多。它占掉 `conversation.abort_at_minutes=15`（900s）的 **2/3**，审阅（120s）与综合（180s）挤在剩下的 300s 里，任何一项超时就顶到 abort。

**修复**（`db/config.py`）：
1. `agent.specialist_timeout` 默认 600 → **300**（覆盖 max 274s，零截断风险）；
2. 新增 `agent.synthesis_timeout=180`，替换 `_stream_final_synthesis` 里的硬编码 `execution_budget(180)`；
3. 加一次性迁移：仅当值仍为 600 时更新为 300，用户自调值不动。

改后预算分配：预处理 60 + 专家 ≤300 + 审阅 120 + 综合 180 ≈ 660s，距 900s abort 留 240s 余量。

`tests/test_conversation_time_limits.py` 的断言从「等于 600」改为「专家阶段 ≤ 总时限一半，且至少给后续留 300s」——锁关系而不是锁魔数。
