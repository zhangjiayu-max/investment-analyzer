## 二、五个根因与对应修复

### 修复1：估值时效性修复（最大失血点）

**根因**：29 条 >80% 分位入场记录说明估值数据滞后/缺失严重。主题指数（H30184 半导体、399808 新能源）不在每日抓取列表。

**修复方案**：
1. `app.py` 新增定时任务：每日 17:00 自动抓取主题指数估值（扩展 `fetch_recent_valuations` 支持的主题列表）
2. `opportunity_engine.py` `_latest_valuation_for_theme` 增加时效性检查：估值 snapshot_date 距今 >3 天则标记 `valuation_stale=True`
3. `_score_theme` 维度4：`valuation_stale=True` 时不加分（保守），并在 `data_freshness` 中暴露估值日期
4. P0-A 估值否决增强：`valuation_stale=True` 时禁 can_buy（降 watch，cap 60），与"无估值数据"同处理

**新增开关**：
- `opportunity.valuation_stale_days_threshold` = 3（估值过期阈值，天）
- `opportunity.valuation_stale_block_can_buy` = true（过期估值禁 can_buy）

### 修复2：主题差异化阈值

**根因**：红利低波（90.9%）和半导体（8.3%）用同一套阈值，成长型主题需要更严格的标准。

**修复方案**：
在 `_score_theme` 中新增主题类型分类函数 `_get_theme_category(theme_name) -> str`：
- `value`：红利低波/红利/价值/蓝筹
- `growth`：半导体/人工智能/新能源/科技/机器人/创新药
- `cycle`：有色/化工/钢铁/煤炭/银行/地产

差异化阈值：
| 主题类型 | can_buy 阈值 | 估值否决阈值 | 估值禁 can_buy 阈值 |
|---------|-------------|-------------|-------------------|
| value | 75（维持） | 80%（维持） | 80%（维持） |
| growth | **82**（提高） | **60%**（收紧） | **60%**（收紧） |
| cycle | 78 | 70% | 70% |

**新增开关**：
- `opportunity.theme_aware_threshold_enabled` = true（主题差异化阈值开关）

### 修复3：降权机制修复

**根因**：半导体连续 miss 12 次但权重仍为 1.0，降权机制空转。

**修复方案**：
1. 修复 `_apply_hit_rate_feedback`：确保降权配置写入 `system_config` 表（当前可能只内存更新未落库）
2. 新增恢复逻辑：连续 2 次 hit → 权重恢复到 1.0（当前代码注释声称有但未实现）
3. 修复 per-source 降权未应用：`_score_theme` 读取 `opportunity.weight_adjust_{source}` 并应用到分数
4. 新增降权日志：降权/恢复时记录到 `opportunity_weight_log` 表（含 theme/source/old_weight/new_weight/reason）

**新增表**：
```sql
CREATE TABLE IF NOT EXISTS opportunity_weight_log (
    id INTEGER PRIMARY KEY,
    scope TEXT,           -- "theme" 或 "source"
    scope_value TEXT,     -- theme名 或 signal_source名
    old_weight REAL,
    new_weight REAL,
    reason TEXT,          -- "consecutive_miss_3" / "consecutive_hit_2"
    consecutive_count INTEGER,
    created_at TEXT
)
```

### 修复4：领先指标维度激活 + 回测字段补全

**根因1**：`opportunity.leading_indicator_score_enabled` 默认 false，领先指标未参与评分。
**根因2**：`capital_signal` 和 `volume_signal` 在 backtests 表全部为 null。

**修复方案**：
1. 激活领先指标维度：`opportunity.leading_indicator_score_enabled` 默认改为 true
2. `_create_opportunity_backtest` 补全字段写入：创建回测记录时同时写入 `capital_signal`/`volume_signal`/`entry_percentile`/`signal_source`
3. `review_opportunity_backtests` 回测时重新评估资金/量能信号（验证"资金流出时降级"是否有效）

**新增开关**：
- `opportunity.leading_indicator_score_enabled` 默认改为 true（从 false 提升）

### 修复5：信号冷却期

**根因**：同一主题 15 天内可能多次发 can_buy，在下跌趋势中连续发信号导致 miss 堆积。

**修复方案**：
`_score_theme` 开头新增冷却检查：
- 同一 theme 15 天内已有 can_buy 记录 → 当前评分 cap 50（强制 watch）
- 同一 theme 15 天内已有 watch 记录 ≥3 条 → 当前评分 cap 65（避免 watch 泛滥）

**新增开关**：
- `opportunity.signal_cooldown_days` = 15（冷却期天数）
- `opportunity.signal_cooldown_enabled` = true

## 三、事件雷达落地验证补全

### 3.1 问题诊断

77 个 materialized 事件只有 25 个被验证，52 个未验证。原因：
1. `verify_materialized_events` 可能只在手动触发或特定定时任务时运行
2. 验证逻辑要求 `materialized_date + T+N` 到期，N 可能设置过长
3. 部分事件的 `affected_sectors` 为空，无法匹配指数验证

### 3.2 修复方案

1. **定时任务加密**：`app.py` 中事件验证定时任务从"每日1次"改为"每4小时1次"（09:00/13:00/17:00/21:00）
2. **补全历史未验证事件**：新增 `backfill_event_verification()` 函数，扫描所有 `status=materialized AND verification_result IS NULL` 的事件，对 `materialized_date + 3天 <= today` 的事件批量补验证
3. **空 affected_sectors 兜底**：验证时如果 `affected_sectors` 为空，从 `affected_themes` 或 `title` 关键词推断板块
4. **验证结果统计修复**：`get_sector_accuracy_stats` 返回的 total 应该是"已 materialized 且到期"的事件数，而非"已验证"的事件数，让用户看到"25/77 已验证"而非只看到 25

**新增开关**：
- `alerts.event_verify_interval_hours` = 4（验证间隔，小时）
- `alerts.event_backfill_verify_enabled` = true（启动时补全历史未验证）
