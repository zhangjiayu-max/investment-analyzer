# 对话 204 超时修复与协同评估

## 故障证据

- 首次失败 trace `8f6b8931-79c`：模型连接经过本机 HTTP 代理时连接被拒绝；与后续执行超时属于不同故障。
- 重新发起 trace `6336d788-c50`：专家已返回初稿，随后各自反思并重写长报告，超出共享 300 秒专家阶段期限。流水线又有统一反思，形成重复审查；整个阶段异常导致未进入综合。

## 本次修复

1. `agent.specialist_timeout` 默认值和运行库配置均设为 600 秒；并行专家共用阶段期限，不是给每个后续模型调用重新发 600 秒预算。
2. `conversation.abort_at_minutes` 默认值和运行库配置均设为 15 分钟。现有生产者仅在收到事件时检查此阈值，不能把它解释为精确的全链路硬截止。
3. 流水线启用统一反思时，专家不再各自完整反思重写；独立专家或关闭统一反思时仍保留自审。
4. 并行阶段超时保留已完成报告及工具证据，对缺席专家写入中立的超时占位；跳过昂贵补审，以降级状态进入综合。全部专家超时则终止，不自动重启 ReAct。
5. 可选反思、辩论超时允许降级汇总；显式取消继续传播。覆盖取消发生在超时占位事件后的情形，以及同批 future 中超时项先返回的竞争。
6. 自审补跑配置钳制为 0–1 次。专家工具循环仍最多 3 轮，文本续写仍最多 2 次，模型重试最多 2 次尝试；这些是有限执行，不是循环直至成功。
7. 修复 ChatInput 失焦事件访问不存在的 `_ctx.setTimeout`。

线程不能被 Python 强制终止。已有有界共享执行器、网络调用期限和后续调用前的预算检查，可限制挂起任务与排队规模；等待超时不表示底层第三方调用已立即停止。综合阶段尚未继承真正的全链路共享截止，后续应统一普通对话与澄清续答的总预算。

## 验证

- 在生产数据库的隔离 SQLite 备份上，以原问题执行真实模型与工具回放，约 315.93 秒获得报告，三个专家均完成；报告因证据/审查不足标记为 `degraded`，没有触发原执行超时，也不生成操作候选。
- 回放仅跳过记忆落库阶段，没有修改对话 204 的失败消息，也没有提交交易。
- 新增/扩展回归覆盖部分专家超时、单 worker 超时竞争、取消优先级、可选审查降级、600 秒配置、有限补跑及前端失焦。
- 最终后端完整回归：`python3 -m pytest -q backend/tests`，1401 passed；前端完整测试 310 passed，生产构建成功。已有依赖弃用及构建包体积警告，不影响本次验证。

## 当前协同方式

阶段总体串行：预处理 → 数据收集 → 计划 → 专家执行 → 统一反思/可选补跑 → 可选辩论/交叉审阅 → 仲裁综合 → 记忆。

数据收集可并行。专家计划至少两步、没有 `depends_on` 且 `pipeline.parallel_execution=true` 时并行；有依赖的计划走顺序路径。当前路由快速生成的计划均为 `depends_on=[]`，各专家接收同一个完整问题，角色分工主要依靠各自配置的提示词。
