# 事件驱动标的发现与估值筛选系统设计稿

> 日期：2026-07-31
> 目标：将"事件雷达"从"预测板块涨跌"升级为"事件→受益标的发现→估值筛选→个性化推荐"
> 核心用户价值：**让用户知道事件发生后该关注哪些标的，结合估值状态判断哪些可以买**

## 一、现状问题与定位调整

### 1.1 当前功能的核心问题

| 问题 | 表现 |
|------|------|
| 定位偏差 | 做的是"事件→预测板块T+3涨跌"，准确率仅 21%，没有实用价值 |
| 输出模糊 | 只输出"板块"（如"半导体"），不输出具体可买的基金 |
| 验证不科学 | T+3 涨跌验证受短期噪音影响大，无法反映事件真实影响 |
| 个性化不足 | 不结合用户持仓/估值状态，所有人看到相同的板块信号 |

### 1.2 新定位

```
旧：事件 → 预测板块涨跌 → 验证准确率（21%，误导用户）
新：事件 → 受益标的发现 → 估值筛选 → 个性化推荐 → 中期逻辑验证
```

**不做的事**：不预测短期涨跌
**要做的事**：发现受益标的 + 结合估值告诉你哪些可以买 + 验证中期逻辑

## 二、核心数据流

```
事件发生（market_events）
    ↓
[层次1] 受益标的发现
    ├── 从 affected_sectors → 映射到受益基金清单
    ├── 从 affected_themes → 关联 theme_rules.funds
    └── 从 event_type → 命中事件类型→标的库
    ↓
[层次2] 估值状态筛选
    ├── 查 index_valuations.percentile
    ├── 标记估值状态：低估(<30%) / 合理(30-60%) / 偏高(60-80%) / 高估(>80%)
    └── 过滤：高估标的不推荐买入（仅展示观察）
    ↓
[层次3] 用户上下文结合
    ├── 持仓去重：已持有的不重复推荐
    ├── 集中度风险：已重仓的提示风险
    ├── 关注列表匹配：已关注的优先提醒
    └── 深套补仓：持仓亏损+低估 → 补仓机会
    ↓
输出：结构化推荐清单
    ├── 强推荐（低估+未持仓+强利好）
    ├── 可关注（合理估值+未持仓+中利好）
    ├── 持仓补仓（低估+已持仓+深套）
    └── 仅观察（高估/已重仓）
```

## 三、数据结构设计

### 3.1 新增表：`event_beneficiaries`（事件受益标的）

存储每个事件的结构化受益标的清单，与 `market_events` 一对多。

```sql
CREATE TABLE IF NOT EXISTS event_beneficiaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id TEXT NOT NULL,              -- 关联 market_events.event_id
    fund_code TEXT NOT NULL,             -- 基金代码
    fund_name TEXT NOT NULL,             -- 基金名称
    index_code TEXT,                     -- 跟踪指数代码
    index_name TEXT,                     -- 跟踪指数名称
    vehicle_type TEXT,                   -- 类型：etf / otc_fund
    benefit_level TEXT NOT NULL,         -- 利好程度：strong / medium / weak
    benefit_logic TEXT NOT NULL,         -- 利好逻辑（一句话说明为何受益）
    valuation_percentile REAL,           -- 估值分位（0-100，NULL=无数据）
    valuation_status TEXT,               -- 估值状态：undervalued / fair / overvalued / expensive / unknown
    is_holding INTEGER DEFAULT 0,        -- 是否已持仓：0/1
    is_watching INTEGER DEFAULT 0,       -- 是否在关注列表：0/1
    recommendation_tier TEXT,            -- 推荐分级：strong_buy / watch / add_position / observe_only
    match_score REAL DEFAULT 0,          -- 匹配评分（0-100，用于排序）
    created_at TEXT DEFAULT (datetime('now', 'localtime')),
    FOREIGN KEY (event_id) REFERENCES market_events(event_id) ON DELETE CASCADE,
    UNIQUE (event_id, fund_code)
);
```

**关键字段说明**：

| 字段 | 取值 | 含义 |
|------|------|------|
| `benefit_level` | `strong`/`medium`/`weak` | 利好程度，由事件类型+板块匹配度决定 |
| `valuation_status` | `undervalued`(<30%) / `fair`(30-60%) / `overvalued`(60-80%) / `expensive`(>80%) / `unknown`(无数据) | 估值状态 |
| `recommendation_tier` | `strong_buy`/`watch`/`add_position`/`observe_only` | 推荐分级，综合利好+估值+持仓得出 |

### 3.2 `recommendation_tier` 推荐分级矩阵

| 利好程度 | 估值低估 | 估值合理 | 估值偏高 | 估值高估 | 无估值 |
|---------|---------|---------|---------|---------|-------|
| **强利好** | strong_buy | watch | observe_only | observe_only | watch |
| **中利好** | watch | watch | observe_only | observe_only | observe_only |
| **弱利好** | observe_only | observe_only | observe_only | observe_only | observe_only |

**持仓补仓例外**：已持仓 + 亏损>15% + 低估 → `add_position`（无论利好程度）

### 3.3 `market_events` 表新增字段

```sql
-- 事件影响时间维度（用于判断验证窗口）
ALTER TABLE market_events ADD COLUMN impact_horizon TEXT DEFAULT 'medium_term';
-- 取值：short_term（1个月内）/ medium_term（1-3个月）/ long_term（3个月以上）
-- 默认 medium_term，由 LLM 在事件提取时判断
```

## 四、核心模块设计

### 4.1 受益标的发现引擎 `services/advisor/beneficiary_finder.py`

**职责**：从事件信息生成结构化受益标的清单。

**输入**：`market_events` 记录（含 `affected_sectors`/`affected_themes`/`event_type`/`direction`）
**输出**：`list[dict]` 受益标的清单

**三级标的发现策略**：

```
策略1：板块→指数→基金（精确映射）
  affected_sectors → SECTOR_TO_INDEX → index_code
  → fund_metadata.tracking_index 反查 → 基金清单
  → benefit_level = medium（板块级匹配）

策略2：主题→基金（主题规则匹配）
  affected_themes → theme_rules.keywords 匹配
  → theme_rules.funds → 基金清单
  → benefit_level = strong（主题级精确匹配）

策略3：事件类型→标的库（兜底）
  event_type=policy + keywords 含"芯片" → 半导体ETF
  event_type=earnings + affected_sectors 含"医药" → 医药ETF
  → benefit_level = weak（类型级兜底）
```

**benefit_level 判定规则**：
- `strong`：主题精确匹配（`affected_themes` 命中 `theme_rules.keywords`）或事件直接关联
- `medium`：板块级匹配（`affected_sectors` 命中 `SECTOR_TO_INDEX`）
- `weak`：仅事件类型级匹配（兜底）

**benefit_logic 生成**：
- 由事件类型+板块+主题组合生成一句话说明
- 示例："SK海力士芯片合作 → 国产替代加速 → 半导体ETF受益"

### 4.2 估值状态筛选器 `services/advisor/valuation_filter.py`

**职责**：为受益标的附加估值状态，过滤高估标的。

**输入**：受益标的清单（含 `index_code`）
**输出**：附加 `valuation_percentile` / `valuation_status` 的清单

**估值数据获取优先级**：
1. `index_valuations` 表本地查询（按 `index_code` + 最新 `snapshot_date`）
2. 估值数据时效检查：`snapshot_date` 超过 3 天标记为 `stale`
3. 无估值数据的标的：`valuation_status = unknown`，不强制过滤

**过滤规则**：
- `valuation_status = expensive`（>80%）→ `recommendation_tier = observe_only`（仅观察，不推荐买入）
- `valuation_status = overvalued`（60-80%）→ 降级推荐（strong_buy → watch）
- 估值数据过期 → 标记 `valuation_stale = true`，不阻塞推荐但提示用户

### 4.3 用户上下文结合器 `services/advisor/context_integrator.py`

**职责**：结合用户持仓和关注列表，生成最终推荐分级。

**输入**：带估值状态的受益标的清单 + 用户持仓 + 关注列表
**输出**：带 `recommendation_tier` / `is_holding` / `is_watching` / `match_score` 的最终清单

**处理逻辑**：

```
对每个受益标的：
1. 查持仓表 portfolio_holdings
   - 已持仓 → is_holding=1
   - 已持仓 + profit_rate < -15% + 低估 → recommendation_tier=add_position（补仓机会）
   - 已持仓 + 重仓（theme_exposure_pct > 10%）→ recommendation_tier=observe_only（集中度风险）

2. 查关注列表 watchlist
   - 已关注 → is_watching=1，match_score +10（用户已关注，优先级提升）

3. 计算 match_score（0-100）
   - benefit_level: strong=40 / medium=25 / weak=10
   - valuation_status: undervalued=30 / fair=20 / overvalued=10 / expensive=0 / unknown=15
   - is_watching: +10
   - is_holding: +5（已持仓说明用户认可）
   - 资金面确认（可选）: +10
   总分上限 100
```

### 4.4 验证逻辑重构 `services/market/event_radar.py`

**当前问题**：T+3 涨跌验证受短期噪音影响，21% 准确率无参考价值。

**新验证策略**：中期相对收益验证

```
旧验证：事件日 T+3 板块涨跌 vs 预测方向
新验证：事件日 T+20 推荐标的 vs 沪深300 超额收益

验证窗口：
- short_term 事件：T+10
- medium_term 事件：T+20
- long_term 事件：T+40

验证指标：
1. 绝对收益：推荐标的在窗口内的涨跌幅
2. 相对收益：推荐标的 - 沪深300 同期涨跌幅（超额收益）
3. 分组验证：按 recommendation_tier 分组看命中率
   - strong_buy 组平均超额收益应 > 0
   - observe_only 组作为对照组

验证结果字段（verification_result V2）：
{
    "status": "correct" / "wrong" / "neutral",
    "abs_return": 5.2,           // 绝对收益%
    "benchmark_return": 1.8,     // 沪深300收益%
    "excess_return": 3.4,        // 超额收益%
    "window_days": 20,
    "verification_method": "relative_return",  // 区分新旧验证
    "fund_results": [            // 每个推荐标的的验证结果
        {
            "fund_code": "159995",
            "fund_name": "芯片ETF",
            "abs_return": 6.1,
            "excess_return": 4.3,
            "tier": "strong_buy",
            "valuation_at_event": 25.3  // 事件发生时的估值分位
        }
    ]
}
```

**验证判定规则**：
- `correct`：strong_buy 组平均超额收益 > +2%
- `wrong`：strong_buy 组平均超额收益 < -2%
- `neutral`：超额收益在 [-2%, +2%] 之间

## 八、与现有系统的集成点

### 8.1 数据复用

| 现有数据 | 用途 |
|---------|------|
| `market_events` | 事件源，新增 `impact_horizon` 字段 |
| `SECTOR_TO_INDEX` | 板块→指数映射，策略1使用 |
| `theme_rules` | 主题→基金映射，策略2使用 |
| `fund_metadata.tracking_index` | 指数→基金反查，策略1使用 |
| `index_valuations.percentile` | 估值状态判定，Phase 2 使用 |
| `portfolio_holdings` | 持仓去重和补仓识别，Phase 2 使用 |
| `watchlist` | 关注列表匹配，Phase 2 使用 |

### 8.2 降级策略

- 无 `theme_rules` 匹配 → 仅用板块级映射（策略1）
- 无 `fund_metadata` 数据 → 回退到硬编码 `_INDEX_FUND_MAP`
- 无 `index_valuations` 数据 → `valuation_status=unknown`，不阻塞推荐
- 无持仓数据 → 跳过持仓相关逻辑，仅输出标的清单

### 8.3 开关控制

所有新功能默认关闭，通过 `system_config` 控制：

| 开关 | 默认值 | 说明 |
|------|--------|------|
| `alerts.beneficiary_finder_enabled` | false | 受益标的发现总开关 |
| `alerts.valuation_filter_enabled` | false | 估值筛选开关 |

## 九、预期效果与成功指标

### 9.1 功能价值

| 指标 | 旧版本 | 新版本（预期） |
|------|--------|---------------|
| 输出形式 | "半导体板块利好" | "芯片ETF(159995) 估值25% 强推荐" |
| 准确率口径 | T+3 涨跌 21% | T+20 超额收益 50%+ |
| 个性化 | 无 | 结合持仓/估值/关注列表 |
| 用户决策价值 | 低（不知道买什么） | 高（直接告诉买什么） |

### 9.2 成功指标

- **推荐覆盖率**：90%+ 的 materialized 事件能生成 ≥3 个受益标的
- **估值筛选率**：80%+ 的受益标的有估值数据（`valuation_status != unknown`）
- **验证准确率**：strong_buy 组 T+20 超额收益准确率 ≥60%
- **分组区分度**：strong_buy 组准确率比 observe_only 组高 15个百分点以上

### 9.3 失败兜底

- 如果受益标的发现覆盖率 <50% → 扩展 `theme_rules` 和 `_INDEX_FUND_MAP`
- 如果估值数据覆盖率 <60% → 扩展 `index_valuations` 数据源
- 如果 strong_buy 准确率 <50% → 调整 `benefit_level` 判定规则或 `match_score` 权重

## 十、风险与限制

### 10.1 已知限制

1. **事件影响的不确定性**：事件→标的的因果关系并非确定性，`benefit_logic` 是基于规则的经验判断，非因果证明
2. **估值数据时效性**：`index_valuations` 依赖人工上传图片解析，可能滞后 3-7 天
3. **基金库覆盖度**：`fund_metadata.tracking_index` 可能不完整，影响指数→基金反查
4. **样本量积累**：T+20 验证需要 20 个交易日后才能验证，初期样本积累慢

### 10.2 缓解措施

- 受益标的发现失败时降级为板块信号（保留现有功能）
- 估值数据过期时标记 `valuation_stale`，不阻塞推荐但提示用户
- 基金库缺失时回退到硬编码映射表
- 初期用 T+10 短窗口快速积累样本，后续切换到 T+20
