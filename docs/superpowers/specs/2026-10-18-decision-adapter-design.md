# 决策档案与决策中心兼容适配设计

日期：2026-10-18

## 目标

让决策中心生成的量化决策进入决策档案，并让决策档案中的接受、暂缓、拒绝、执行、复盘状态同步回量化账本。保留现有两张表及历史数据，避免一次性迁移带来的风险。

## 当前边界

- `decision_records` 是用户工作流记录，关联候选建议、行动项、复盘反馈和时间线。
- `investment_decisions` 是量化账本，保存信号快照、置信度、建议金额、风控、止盈计划和回测结果。
- 两张表的主键不能直接视为同一个 ID。
- 本阶段不做自动调度、不重构策略算法、不删除旧表。

## 统一对象与关联

在 `investment_decisions` 增加 `decision_record_id`，指向 `decision_records.id`；在 `decision_records` 增加 `investment_decision_id`，形成可追溯的双向关联。关联字段允许为空，以兼容历史数据和纯人工决策。

新流水线完成量化账本写入后，创建一条对应的 `decision_records`，将信号、风控、证据、建议金额和复盘日期转换成档案字段。创建操作必须幂等：同一个 `investment_decision_id` 已有档案时返回原记录，不重复创建。

## 状态映射

| 量化账本状态 | 档案状态 | 说明 |
|---|---|---|
| `suggested` | `proposed` | 系统提出建议，等待用户决定 |
| `confirmed` | `accepted` | 用户确认接受 |
| `executed` | `executed` | 已有实际执行或用户确认执行 |
| `closed` | 保留用户状态，新档案为 `proposed` | 只标注量化回测完成，不伪造用户复盘 |
| `expired` | `expired` | 超过有效期 |

档案状态 `rejected`、`deferred` 没有量化账本的等价状态，适配层将其记录为量化账本的 `notes` 事件，并保留账本当前状态，避免把“用户暂不执行”误记成“量化建议失效”。

## 同步规则

1. 档案接受或执行时，同步量化账本为 `confirmed` 或 `executed`。
2. 档案暂缓、拒绝时，不改变量化账本状态，只追加同步事件和用户备注。
3. 档案复盘时，如果存在量化账本，写入用户复盘摘要；量化回测结果仍写入原有回测字段。
4. 量化回测关闭账本时只追加完成说明；用户复盘独立提交，用户复盘也不关闭尚待回测的量化账本。
5. 时间线独立显示用户状态、行动和量化回测结果；完整不可变状态事件留到后续阶段。

## API 与前端行为

- 增加适配层查询接口，返回统一对象并携带 `decision_record` 与 `investment_decision` 的关联信息。
- 决策中心的账本行增加“打开决策档案”入口；没有档案时提供“创建档案”操作。
- 决策档案详情显示量化信号、建议金额、风控、止盈计划和回测结果；没有关联账本的人工决策继续按旧逻辑展示。
- 两页统计明确分开“用户复盘反馈”和“量化回测命中率”，避免混为一个胜率。

## 迁移与失败处理

- 初始化时使用 `ALTER TABLE ... ADD COLUMN` 的兼容迁移，重复执行安全。
- 历史数据不自动按模糊条件强行合并；只提供明确关联和可审计的候选匹配结果。
- 适配同步失败不阻断原有决策流水线，记录日志并在 API 返回 `sync_status`，前端提供重试入口。
- 所有新同步逻辑使用参数化 SQL，并为重复请求增加唯一性检查。

## 验收标准

- 运行一次决策流水线后，决策中心和决策档案能看到同一条决策的关联信息。
- 在决策档案接受、执行、复盘后，量化账本状态和用户复盘字段符合映射规则。
- 重复刷新或重复同步不会创建重复档案。
- 旧的人工决策、旧的量化账本和现有回测测试全部保持通过。

## 本阶段验证与后续

- 用户归属随量化账本保留；双向关联和状态更新校验归属一致。
- 共用状态入口在单个 SQLite 事务中更新两套记录，覆盖交易草稿和确认调用。
- 并发创建竞争时复用成功关联，清理多余档案及行动项。
- 买入草稿保留建议金额；减仓必须有明确份额，不从持仓擅自推导全仓卖出。
- 后端目标回归、前端决策/审计/移动导航测试及生产构建通过。
- B 阶段继续补提醒去重、执行证据与到期复盘；现有每日量化回测定时任务继续复用。
